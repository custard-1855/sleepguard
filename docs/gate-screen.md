# ロック中の確認画面 仕様(Android)

2026-10-26 に合意した仕様。同日に実装した。2026-11-09 に緊急解除をなくし、電話と Cosense を開けるようにした。

## 目的

1時以降のロックが始まると、解除するたびにすぐロックされ、緊急通報(110・119)以外の連絡ができない。
#7119 や家族への連絡など「急ぐが通報ではない」ときのために、電話のアプリは夜中も使えるようにする。
あわせて、音声を聴くためのアプリと Cosense も夜間に使えるようにする。
寝る前にアラームを設定できるように、時計のアプリも使えるようにする(2026-10-26 追加)。

## 全体

- ロックの対象になったら(1時の通知から10分後も使っていたら)、すぐロックする代わりに確認画面を出す
- 確認画面のボタンは「ロックする」「音声を聴く」「Cosenseを開く」「電話をかける」「アラームを設定」。アプリのボタンは、そのアプリが入っているときだけ出す
- 開いたアプリが前面にあるあいだは、時間に関係なくロックしない。ほかのアプリが前面に来たら、普段どおり確認画面を出す。回数の制限はない
- 確認画面で10秒操作がない、ホームや履歴で離れる、戻るを押す → ロックする
- 確認画面を出せなかったとき(OEM の制限など)は、15秒たって次に評価したときに普段どおりロックする
- 確認画面が出る前に画面を消したら、次に使ったときにまた確認画面を出す
- 確認画面からアプリを開けなかったときはロックする。確認画面で落ちると、同じプロセスのユーザー補助サービスごと止まり、システムが接続し直さないため
- ホーム画面と履歴の画面は前面の切り替えとみなさない(2026-10-26 変更。当初はホーム画面でも確認画面を出していた)。履歴からスワイプでアプリを閉じられるようにするため。ホーム画面からほかのアプリを開けば、確認画面を出す

## 音声を聴く・Cosenseを開く

アプリ画面で選ぶアプリ。コード上は `ChosenApp` に並べてあり、足すときはここに1行足す。

- 開くアプリは、アプリ画面の「音声のアプリを選ぶ」「Cosenseのアプリを選ぶ」でホーム画面のアプリの一覧から選ぶ。音声のアプリの名前はコード・ドキュメント・画面に書かない(アプリ画面の状態表示も「選択済み」とだけ出す)
- Cosense にはネイティブのアプリがないので、ブラウザでホーム画面に追加した Cosense(PWA)を選ぶ。PWA は独自のパッケージ名を持つので、ブラウザ本体とは区別してロックの判定ができる。ブラウザ本体は選ばない(そのブラウザで何を見ていてもロックしなくなるため)
- 1時〜6時はアプリを選び直せない(その場でロックを抜けられてしまうため)
- ボタンを押すと選んだアプリを開く。確認はしない
- 回数の制限はしない(2026-10-26 変更。当初は一晩1回だった)
- そのアプリが前面にあるあいだは、時間に関係なくロックしない。画面を消して再生を続け、また点けてそのアプリに戻るのはかまわない
- ほかのアプリが前面に来たら、普段どおり確認画面を出す。そこからまたボタンで戻れる
- 記録はしない。ボタン名と通知に目的は書かない
- アプリを選んでいないか、選んだアプリが入っていなければボタンを出さない

## 電話をかける

2026-11-09 に追加した。それまでの緊急解除(30秒待って30分ロックを外す。使った時刻を記録)の代わり。
電話を直接開けるなら、ロックをまるごと外す手順は要らず、記録も要らない。

- 端末の標準の電話のアプリ(`TelecomManager.defaultDialerPackage`)を開く。アプリは選ばせない
- 開くときは、ホーム画面から開くときと同じ intent を使う
- 回数の制限はしない。電話のアプリが前面にあるあいだはロックしない
- ほかのアプリが前面に来たら、普段どおり確認画面を出す(ホーム画面と履歴の画面は除く)
- 電話のアプリが見つからなければボタンを出さない
- 110・119 は、これを通さずロック画面の「緊急通報」からもかけられる。ロック時の通知でそう案内する

## アラームを設定

2026-10-26 に追加した。

- 端末の標準の時計のアプリを開く。アプリは選ばせず、アラームの一覧の intent(`AlarmClock.ACTION_SHOW_ALARMS`)を受けるアプリで決める
- 開くときは、ホーム画面から開くときと同じ intent を使う。ColorOS の時計はアラームの一覧の intent でも `SET_ALARM` の権限を求め、SleepGuard はその権限を持たないため
- 回数の制限はしない。時計のアプリが前面にあるあいだはロックしない
- ほかのアプリが前面に来たら、普段どおり確認画面を出す(ホーム画面と履歴の画面は除く)
- 時計のアプリが見つからないか、複数あって標準が決まっていない(選択画面になる)ときはボタンを出さない

## 前面のアプリの判定

- ユーザー補助で `typeWindowStateChanged` を受け取り、イベントのパッケージ名だけを使う。画面の内容は読まない(`canRetrieveWindowContent` は false のまま)
- システム UI(通知シェードなど)、入力方法(キーボード)、SleepGuard 自身のイベントは前面の切り替えとみなさない
- 画面全体を覆わないウィンドウのイベント(`isFullScreen` が false)も見ない。ランチャーはアプリを開いた直後にも部品(`ScrollView` など)のイベントを出すので、拾うと開いたアプリの上に確認画面が出てしまう(2026-10-26 に OPPO 実機で確認)
- ホーム画面のアプリ(`CATEGORY_HOME`)のイベントも見ない。OPPO 実機では履歴の画面もホーム画面のアプリが出し、両者はイベントの文言でしか見分けられないので、まとめて外す
- 前面のアプリは保存しておき、ユーザー補助サービスが接続し直したとき(アプリの更新、プロセスの再起動など)に読み戻す。保存しないと接続直後は前面のアプリがわからず、開いたアプリの上に確認画面が出てしまう
- 前面のアプリが変わったら時間割を評価し直す

## 実装メモ

- 判定は `Guard` に置き、`GuardTest` でテストする。`Device` に前面のアプリ、確認画面を出しているか、端末の標準の時計と電話のアプリを持たせる。選んだアプリは `State` から読む
- 確認画面は `GateActivity`。ユーザー補助サービスはバックグラウンドからの Activity 起動の制限の例外なので、`LockService` から開ける見込み。OPPO 実機で確かめる
- ロック時の通知(電話と「緊急通報」の案内つき)は、確認画面からロックするときも出す
- 緊急解除が保存していた `emergencyUntil` と `emergencyLog` は、読まなくなっただけで消していない
